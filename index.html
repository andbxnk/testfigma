บทเรียนที่ 1: UX Process & Problem-Solving Methodology

กระบวนการคิดออกแบบ UX: Research, Pain Point, HMW และ User Flow

เรียนรู้ที่มาของข้อมูลวิจัย, เทคนิคการสกัดปัญหาที่แท้จริง (Root Cause Analysis), การตั้งคำถามเปิดกว้าง How Might We (HMW) และการเขียน User Flowchart ด้วยสัญลักษณ์มาตรฐานสากล

1.1 User Research มาจากไหน? (วิจัยเชิงคุณภาพ vs เชิงปริมาณ)

การเก็บข้อมูลผู้ใช้จากแหล่งข้อมูลขั้นต้น (Primary) และขั้นภูมิภาค (Secondary)

Research Foundations

Primary Research (วิจัยตรงจากผู้ใช้จริง)

  • •
    Qualitative (เชิงคุณภาพ - เน้นความรู้สึก "ทำไม"):

    User Interviews, Contextual Inquiry (ลงพื้นที่สังเกตการณ์ทำงานจริง), Usability Testing (ดูคนใช้งานจริงเพื่อหาจุดติดขัด)

  • •
    Quantitative (เชิงปริมาณ - เน้นสถิติตัวเลข "มากเท่าไร"):

    แบบสอบถามออนไลน์ (Surveys), Google Analytics (อัตรา Drop-off), A/B Testing

ตัวอย่างจริง: สัมภาษณ์ผู้โดยสารรถไฟฟ้า 15 คน พบว่า 80% บ่นว่าปุ่มเติมเงินในแอปค้นหายาก และใช้เวลากดเฉลี่ยมากกว่า 45 วินาที

Secondary Research (การวิจัยจากข้อมูลที่มีอยู่แล้ว)

  • •
    Competitor Analysis: วิเคราะห์จุดแข็ง-จุดอ่อนของแอปคู่แข่งในตลาด
  • •
    App Store / Play Store Review Mining: ขุดอ่านคำบ่นระดับ 1-2 ดาวใน App Store เพื่อดูสิ่งที่ผู้ใช้ไม่ชอบ
  • •
    Industry Market Reports: รายงานพฤติกรรมผู้บริโภคจากสถาบันวิจัย
ตัวอย่างจริง: ขุดอ่านรีวิวแอปส่งอาหารคู่แข่ง พบผู้ใช้บ่นว่า "กดยกเลิกออเดอร์ไม่ได้ทันทีหลังกดสั่งผิด" มากกว่า 200 คอมเมนต์

1.2 Pain Points มาจากไหน? & การสกัดปัญหาด้วย 5 Whys Analysis

เปลี่ยนคำบ่นตื้นๆ ให้กลายเป็นสาเหตุรากเหง้า (Root Cause) เพื่อแก้ปัญหาตรงจุด

Problem Discovery

เครื่องมือสังเคราะห์ Pain Point:

1. Empathy Map (4 ช่อง):

จำแนกข้อมูลที่ได้จากวิจัยออกเป็น Says (สิ่งที่พูด), Thinks (สิ่งที่คิด), Does (การกระทำ) และ Feels (ความรู้สึกอารมณ์) เพื่อมองเห็นความขัดแย้งของผู้ใช้

2. Affinity Diagram:

การนำ Sticky Notes ข้อร้องเรียนจำนวนมากมาแปะรวมกลุ่ม (Clustering) ตามรูปแบบพฤติกรรมที่คล้ายกัน เพื่อค้นพบแพตเทิร์นปัญหาใหญ่

เคสตัวอย่างจริง: 5 Whys Analysis

สถานการณ์: ผู้ใช้ละทิ้งตะกร้าสินค้าในหน้าชำระเงิน (Drop-off 40%)

Why 1: ทำไมผู้ใช้ถึงกดออกจากหน้าชำระเงิน? → เพราะตกใจยอดเงินรวมที่สูงเกินคาด

Why 2: ทำไมยอดเงินรวมถึงสูงเกินคาด? → เพราะมีค่าบริการและค่าจัดส่งบวกเพิ่มเข้ามาในขั้นตอนสุดท้าย

Why 3: ทำไมผู้ใช้ถึงไม่รู้ค่าจัดส่งล่วงหน้า? → เพราะระบบไม่คำนวณค่าส่งให้จนกว่าจะกรอกที่อยู่ครบถ้วน

Why 4: ทำไมถึงต้องรอสแกนที่อยู่ก่อน? → เพราะ UX ออกแบบให้ใส่ที่อยู่เป็นขั้นตอนสุดท้าย

Why 5 (Root Cause): ระบบขาดการประเมินราคาและค่าส่งแบบโปร่งใสล่วงหน้าก่อนเข้าสู่ Checkout!

1.3 เปลี่ยน Pain Point เป็น HMW (How Might We) และคิดโซลูชัน

เปลี่ยนคำบ่นเชิงลบ ให้กลายเป็นคำถามชวนคิดสร้างสรรค์ในเชิงบวก

Ideation Framework
STEP 1: PAIN POINT

"ผู้ใช้รู้สึกหงุดหงิดที่ต้องกรอกข้อมูลบัตรเครดิตและที่อยู่ใหม่ทุกครั้งที่ต้องการกดสั่งซื้อรายการโปรดเดิมๆ"

STEP 2: HMW QUESTION

"How Might We..."
"เราจะทำอย่างไรให้ผู้ใช้สามารถสั่งซื้ออาหารรายการโปรดซ้ำได้ภายใน 1 คลิก โดยไม่ต้องกรอกข้อมูลเดิม?"

STEP 3: FEATURE SOLUTION

ออกแบบฟีเจอร์ "1-Click Quick Re-order" บนหน้าแรก พร้อมบันทึกวิธีชำระเงินตั้งต้น (Default Payment) อัตโนมัติ

บทเรียนที่ 2: Figma Core Tools, Shortcuts & Symbols Summary

สรุปเครื่องมือ Figma, สัญลักษณ์ (❖, ◇, ❖❖), Auto Layout และจุดหลอกข้อสอบ

รวมสัญลักษณ์ทุกเครื่องมือ คีย์บอร์ดลัด กฎการ Override ของ Component และตารางเปรียบเทียบเชิงลึกเพื่อทำข้อสอบได้เต็ม

2.1 Auto Layout (Shift + A) & Resizing Rules

การจัดระเบียบโครงสร้าง UI แบบ Responsive อัตโนมัติ

Shift + A
Hug Content หดรัดตามเนื้อหา

ขนาดของ Frame จะปรับยืดหดตามขนาดของวัตถุหรือข้อความข้างใน + ระยะ Padding
เหมาะสำหรับ: ปุ่มกด (Buttons), Badges, Tags ที่ข้อความยาวไม่เท่ากัน

Fill Container ยืดเต็มพื้นที่

วัตถุลูกข้างในจะยืดขยายเติมเต็มพื้นที่กว้าง/สูงของ Frame แม่ตลอดเวลา
เหมาะสำหรับ: การ์ด UI แบบ Responsive, บรรทัดข้อความยาวๆ ในการ์ด

Fixed Width / Height ล็อกขนาดพิกเซล

กำหนดขนาดพิกเซลคงที่แน่นอน ไม่ยืดและไม่หดตามวัตถุข้างในหรือ Frame แม่
เหมาะสำหรับ: ไอคอนขนาดมาตรฐาน (24x24 px), รูป Avatar ทรงกลม

2.2 Main Component (❖) vs Instance (◇) & กฎการ Override

ความสัมพันธ์แบบแม่พิมพ์หลักกับชิ้นงานลูก และสิ่งที่แก้เฉพาะตัวได้/ไม่ได้

Design System Core
คุณสมบัติ Main Component (❖) Instance (◇)
สัญลักษณ์ ❖ เพชรทึบ 4 เม็ด ◇ เพชรโปร่ง 1 เม็ด
บทบาท ต้นแบบแม่พิมพ์หลักควบคุมสไตล์ ชิ้นงานลูกที่คัดลอกไปวางกระจายใช้งาน
การแก้ไข แก้ที่นี่ เปลี่ยนตามทั้งโปรเจกต์ ปรับแก้เฉพาะตัวได้ด้วยการ Override
คีย์บอร์ดลัด Cmd+Opt+K / Ctrl+Alt+K Alt + Drag / Duplicate

กฎการ Override บน Instance (◇):

✓ สิ่งที่ Override แก้ไขเฉพาะตัวบน Instance ได้:
ข้อความ (Text Content), สี Fill/Stroke, Drop Shadow Effects, รูปภาพ และการสลับ Variant / Instance Swap
✕ สิ่งที่ห้ามแก้บน Instance (ต้องแก้ที่ Main แม่เท่านั้น):
การย้ายสลับตำแหน่ง Layer ข้างใน, การลบ Layer ข้างในทิ้ง หรือการเปลี่ยนทิศทาง Auto Layout

* คำสั่ง Detach Instance (Cmd+Opt+B) คือการตัดสายสะดือความสัมพันธ์ออกจาก Main เปลี่ยนให้เป็น Frame ธรรมดา

❖❖ Variants & Component Sets

เป็นการรวม Component ชนิดเดียวกันที่มีหลายสถานะ (เช่น ปุ่ม Default, Hover, Pressed, Disabled) เข้าไว้ในกรอบเส้นประเดียวกัน (Component Set ❖❖) เพื่อง่ายต่อการเลือกสลับ State บน Inspector Panel

Properties: Property 1 = Hover, Size = Large, State = Active

# Frame vs [ ] Group

Frame (#): มีขอบเขต مستقل (Independent Bounds) สามารถใส่ Auto Layout, Layout Grid, Clip Content และ Constraints ได้
Group ([ ]): เป็นเพียงการรวมกลุ่มวัตถุ ขนาดขอบจะหดขยายสเกลตามวัตถุข้างในเสมอ ไม่สามารถใส่ Clip Content หรือ Auto Layout โดยตรงได้
